# 0028 — MCP server, per-run tokens, read tools and frames rendered by the renderer

- Status: Accepted
- Date: 2026-11-08

## Context
ADR-0003 decided that AI agents act only through an MCP server embedded in se-core, with a token per task; ADR-0027 built the task runtime with `AgentRunSpec.mcp` still optional. Prompt 18 gives agents eyes: a real server at `/mcp`, authenticated per task, and read tools that let an agent understand a project before acting — its timeline, its media and their analyses, and above all **what the sequence looks like**, texts and animations included. Open questions: which MCP library and transport, how a token is bound to a task and checked, how tools are organised and what they return to stay cheap in tokens, how times cross the boundary, and how the core — which cannot composite (the engine lives in the renderer, golden rule 7) — returns pictures of the sequence.

## Decision
- **Server.** `rmcp` 3.9 (the official Rust SDK), streamable HTTP service (`StreamableHttpService`, sessions in memory closed after 5 minutes idle) mounted by se-core at `/mcp`. `McpServer` implements `ServerHandler` by hand (`tools/list`, `tools/call`) over our own registry instead of rmcp's tool macros, so each tool is one file and the catalogue is a plain list. Server name `simpleeffect` (Claude Code exposes `mcp__simpleeffect__<tool>`).
- **Tokens per run.** `se_app::TaskTokenRegistry` mints a 256-bit token (`TokenSource` port, se-core's CSPRNG) when a run starts, bound to an `AgentContext { project_id, task_id, run, scope }`, and revokes it when the run ends (a guard dropped on every exit path). `AgentRunSpec.mcp` is now required: the run's spec carries `http://127.0.0.1:<port>/mcp` and its token. Follow-ups and retries get fresh tokens.
- **Two checks.** `/mcp` is outside the session-token guard (agents never see the app's token) and has its own middleware in se-core: `Host` must be `127.0.0.1:<port>` or `localhost:<port>` (403), `Authorization: Bearer` must name a running run (401 with `WWW-Authenticate: Bearer`) — unknown and revoked tokens are refused before any MCP message is read. The handler resolves the token again for every tool call (a run that ended in between gets `ACCESS_REVOKED`). Tokens are never logged; tool calls are logged with tool, task, duration and error code.
- **Claude Code.** The provider always passes the inline config (`--mcp-config` `{"type":"http","url":…,"headers":{"Authorization":"Bearer …"}}`, redacted in logs), `--strict-mcp-config` and `--allowedTools "mcp__simpleeffect__*"`; built-in tools stay off (`--tools ""`).
- **Tool contract** (`docs/ai-tools.md`, the reference). One tool per file implementing `McpTool { Input: Deserialize + JsonSchema, NAME, DESCRIPTION, READ_ONLY, call }`; input schemas generated by `schemars` (unknown fields refused); `snake_case` names everywhere except `get_item`'s `properties` (the document form). Outputs are one compact JSON text block, then images. Times in: seconds or timecode strings (`se_domain::parse_timecode`, frames at the sequence's rate); times out: `{"timecode": "HH:MM:SS.mmm", "seconds": n}` (`se_domain::format_clock`). Outputs carry ids and revisions; long lists are paginated (`offset`/`limit` → `next_offset`). Errors are tool results flagged `isError` with a stable code and an actionable message (use-case errors keep their protocol code); an unknown tool is a protocol error. Tools default to the task's sequence and range.
- **Read tools** read through se-app use cases only — `ProjectService::project` (the current document), `MediaService::analysis` (stored analyses of the current content), `MediaService::frame_jpeg` (ffmpeg frames, `MediaFiles::read_file`), `FrameRenderService::render` — and change nothing: `get_project_overview`, `get_timeline`, `get_item`, `list_assets`, `get_frames`, `get_source_frames`, `get_audio_analysis`, `get_scene_changes`, `list_animation_presets` (the domain's library), and explicit stubs answering `available: false` for `get_transcript` (prompt 21), `get_brand_kit` (25) and `list_templates` (24). Analyses asked for a range of the sequence are brought back from source time through each clip's source window and speed; the silences of a range are where no unmuted sound clip is heard (unanalysed clips count as sound).
- **Frames of the sequence come from the renderer.** `FrameRenderService` (se-app) checks the request (≤ 16 frames, size from the sequence's aspect, `frame_size`), refuses at once when no renderer is connected (`RendererLink` port: se-core's event bus, connected while an `/rpc` socket is open), publishes `renderFramesRequested { requestId, projectId, sequenceId, times, width, height }` and waits ≤ 30 s. The renderer (`useAgentFrameRequests`, mounted by `AppLayout` so it always answers) draws each time with `@se/engine`'s new `StillRenderer` — the viewer's `FrameRenderer` and Pixi compositor on its own `OffscreenCanvas` and decoder pool, proxies up to 960 px wide, fonts from the catalogue — and uploads one JPEG per frame with `PUT /media/renders/{requestId}/{index}` (session-token guard, CORS for that route only, ≤ 8 MiB, JPEG checked), or answers `reportFrameRenderFailure { requestId, message }` (another project shown, sequence unknown, decoding failed). The service answers the agent once every frame arrived (in time order), forgets requests whose caller stopped waiting, and refuses late uploads (`RENDER_REQUEST_NOT_FOUND`). New codes: `RENDERER_UNAVAILABLE`, `RENDER_FAILED`, `RENDER_REQUEST_NOT_FOUND`.
- **Agent instructions** are three provider-agnostic files (`00-role.md`, `01-time-and-scope.md`, `02-reading-the-project.md`), composed with the task's scope (timecodes, track names) and a summary of the project (sequences with format and length, tracks of the task's sequence, media counts) into the run's system prompt file.

## Consequences
- An agent can describe a sequence from pictures identical to the viewer's and the export's (one engine), check timing against analyses, and cite ids and timecodes the user finds in the timeline.
- `get_frames` needs an editor window showing the project; otherwise the agent gets an actionable error at once (no window) or after 30 s (a window that cannot answer). Frames never touch the disk.
- Write tools (prompt 19) plug into the same registry, `AgentContext` (scope checks) and conventions (revisions for optimistic concurrency); `docs/ai-tools.md` and the schema snapshots are the contract to update.
- rmcp's breaking releases now matter: the server uses only `ServerHandler`, `StreamableHttpService`, model types and (in tests) the reqwest client; the integration test in `crates/se-core/src/mcp_routes.rs` drives a real rmcp client against the route.
- The token lookup is a hash map access keyed by the candidate (keys hashed with random seeds), not a constant-time comparison; with 256-bit secrets and a loopback-only listener this leaks nothing usable.

## Alternatives considered
- **rmcp's `#[tool_router]` macros**: one `impl` block holding every tool, against our one-tool-per-file rule; schemas and errors would follow the macro's conventions instead of ours. Rejected.
- **Checking the token only inside the MCP handler**: unknown callers could still open sessions and list tools. Rejected for an HTTP-level 401 plus a per-call check.
- **Stateless MCP (no sessions)**: simpler, but clients negotiating older protocol versions (Claude Code's) expect the `initialize` handshake and a session; rmcp serves both modes and its default session mode worked with the real CLI. Kept the default.
- **Compositing in the core (a Rust renderer)**: a second renderer that would drift from the viewer (WYSIWYG). Rejected (ADR-0002).
- **Sending JPEGs back over the `/rpc` socket as base64**: a third larger and every frame through JSON; binary belongs on `/media` (the prompt's route). Rejected; the CORS preflight of the `PUT` is answered for that route only.
- **Images on disk (the cache) handed to the agent as paths**: agents have no file access (golden rule 2). Rejected for MCP image content.
