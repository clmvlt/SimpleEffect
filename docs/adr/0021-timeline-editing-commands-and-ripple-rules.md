# 0021 — Timeline editing: intent commands, edit plans, placement and ripple rules

- Status: Accepted
- Date: 2026-11-07

## Context
Prompt 11 makes the timeline editable with the mouse and the keyboard: dropping media from the bin, moving (Alt copies), trimming (with or without ripple), cutting at the playhead, deleting (with or without ripple), copy/cut/paste, nudging by frames, linking, and lengthening or shortening gaps — each gesture one undo step, with the renderer previewing and the core deciding. Open questions: what the protocol carries (a generic list of domain operations, or one command per intent), how a gesture of several operations stays one transaction and stays fast on large sequences, what an overwrite does to what lies under a clip, and which tracks a ripple edit shifts (the domain has no « sync lock »).

## Decision
- **One protocol command per intent**, always actor `User`, one transaction each: `placeMedia`, `moveItems`, `duplicateItems`, `pasteItems`, `trimItems`, `splitItems`, `deleteItems`, `linkItems`, `unlinkItems`, `resizeGap`. The renderer sends target positions (it previews and snaps); the core generates every id (items, split parts, link groups, new tracks), names new tracks, labels the transaction and validates. A generic « apply these operations » command was rejected again (ADR-0020): ids, labels and rules would leak into the renderer. These use cases are what the MCP write tools (prompt 19) will call.
- **Edit plans.** `se-app` plans a gesture with `EditPlan`: operations are queued and applied to a draft of the document only when the planner reads it (`se_domain::apply_all`), so later steps are planned against the state earlier ones leave (what lies under a clip once it is lifted). The actor then commits the queue as one transaction. `se_domain::commit` validates the document **once, after the last operation** (each operation still checks its own preconditions): validating after every operation made a 500-item move take 0.8 s in release (1.8 s in debug); it now takes 3 ms.
- **Placement modes.** `overwrite` (default): placed items replace what they cover on their own tracks — covered items are removed, partly covered ones trimmed, an item spanning the placed one cut around it; items linked to them on other tracks stay. `insert` (Ctrl/⌘): time as long as the placed block opens at its earliest start on the concerned tracks (below), cutting items that cross that point. Moves lift the moved items first (so they never collide with themselves), then place them. Dropped media lasts its full duration (images 5 s, `DEFAULT_IMAGE_DURATION` on both sides); a video with sound becomes two linked items on the hovered track and the track of the other kind with the same number (V2 ↔ A2), a new track when it does not exist or when dropped below the last track.
- **Ripple scope = concerned tracks.** A ripple edit (ripple delete, ripple trim, gap resize, insert) shifts what follows its edit point on the tracks it edits plus — until nothing is added — every unlocked track holding an item linked to an item that moves, so linked picture and sound never drift apart. Other tracks stay (a title track is not dragged along by a cut in the interview). Locked tracks never move: a locked edited track refuses the edit, a locked partner track is left out (lock a track to keep it still). Removing time is **refused** with `RIPPLE_BLOCKED` when a concerned track holds other content in that time, rather than cutting it silently. A ripple delete groups tracks whose concerned sets meet; each group loses the union of its deleted items' ranges.
- **Ripple trims** move edges sitting at one instant (an item and its linked partners) to one place; the trimmed items keep their position (a ripple trim of a start extends or shortens the clip at its start and shifts what follows). The renderer trims linked partners together only when their edge is at the same instant (Alt: the item alone).
- **Gaps** are computed, never stored: the empty time between the previous item (or 0) and an item on one track. Clicking one selects it (shaded, with its length); its handle at the end lengthens or shortens it, `Suppr` (or « Fermer le blanc ») closes it — `resizeGap` opens or removes time at its end on the concerned tracks.
- **Gestures in the renderer.** One pointer handler on the lanes (`use-lane-pointer.ts`) dispatches a press to the selection, the rectangle or a gesture controller (`hooks/gestures/`: move, trim, gap handle; `use-media-drop.ts` for drops). While dragging, the controller writes an ephemeral preview (`gesture-store`: items drawn elsewhere, ghosts of new items, the snap point) and sends nothing; on release one command; the preview clears when the command resolves (se-core sends the patch before the response) or fails (translated toast, with a precise message for common domain refusals). Escape cancels a drag. Pure computations — snapping, track offsets, trim limits, drop targets, ripple previews (a port of the concerned-tracks rule), clipboard mapping — live in `services/`. Dragged edges move by whole frames and snap within 8 px to the playhead, item edges, markers and in/out points (`N` toggles snapping, which moved from `S`: `S` now cuts).
- **Click semantics move to the release.** Pressing an item that is already selected keeps the selection (a drag then moves all of it); replace, Ctrl/⌘ toggle-off and Alt « alone » apply when the press ends without a drag.

## Consequences
- Every gesture is exactly one transaction and one undo step, whatever its number of domain operations; the journal stores primitive, replayable operations.
- A transaction may pass through states only its later operations repair (e.g. an item briefly before zero); stored states are always valid.
- Ripple edits are predictable without a sync-lock setting; when the default is not wanted, locking a track excludes it. A per-track sync lock can be added to the document later (backlog).
- The renderer's ripple preview duplicates the concerned-tracks rule for display only; when the core refuses (`RIPPLE_BLOCKED`), the preview simply disappears with a toast.
- Copies made by the user (duplicate, paste, Alt+drag) are `origin: user` items, even when the original came from an AI task.

## Alternatives considered
- **A generic `applyEdit { ops }` command**: smallest protocol surface, but the renderer would build domain operations, generate ids and labels, and re-implement overwrite and ripple logic — the duplication ADR-0005 forbids.
- **Sequential `MoveItem`s for multi-item moves**: half the operations, but items swapping places (dragging a selection over itself, across tracks) need an ordering and sometimes a temporary place; lifting then placing is always valid.
- **Ripple on every unlocked track** (Premiere's default sync lock): keeps everything in sync, but a ripple delete in the interview would be refused (or cut the music) whenever another track has content there. Rejected as the default; linked tracks follow instead.
- **Overwrite refuses instead of trimming**: safer but makes dropping onto existing clips useless; NLE users expect overwrite to replace.
- **Validating after every operation (previous behaviour)**: kept every intermediate state valid but cost a full document validation per operation.
