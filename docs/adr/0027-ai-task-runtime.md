# 0027 — AI task runtime: task service, runs and sessions, Claude Code invocation and isolation

- Status: Accepted
- Date: 2026-11-07

## Context
ADR-0003 chose to run AI agents through the CLI installed on the user's machine (Claude Code first), behind an `AgentProvider` trait, with MCP as the only way to act on the project. Prompt 17 builds the runtime under that decision, before any MCP tool exists: tasks submitted in the background, several at once with a limit, cancellable, retryable and continuable (follow-ups resuming the agent's session), persisted with their event logs, surviving a core restart; and the Claude Code adapter itself. Open questions: where tasks live and how they are scheduled, what a run and a session are, how a CLI process gets its prompt and instructions on every OS, how isolated an agent is from the user's own CLI configuration while still using their subscription login, how the app knows whether the CLI is installed and logged in, and how the UI talks about a provider without naming a CLI.

## Decision
- **One task service.** `se_app::TaskService` (the architecture's `TaskScheduler`) holds the tasks of every open project and one FIFO queue of runs shared by all of them; at most `maxConcurrentTasks` runs at once (AI setting, 1–8, default 3; a raised limit starts waiting runs at once, a lowered one lets running runs finish). It observes projects (`ProjectObserver`): tasks load when a project opens and are cancelled (≤ 8 s wait) when it closes. Task state sits behind one async mutex held while a change is saved, so saves of a task never overtake each other; event appends happen outside it.
- **Tasks, runs, statuses.** A `Task` (protocol DTO) is a request with a prompt, a `TaskScope` (sequence, optional range, optional tracks — checked against the project at submission), a provider, an optional model and effort (defaults from the settings) and a list of runs. Each `TaskRun` (`initial`, `retry`, `followUp`) has its prompt and status; the task's status is its latest run's: `queued → running → completed | failed { failure, message } | cancelled`. Retrying needs a finished task (`TASK_STILL_ACTIVE` otherwise), cancelling an active one (`TASK_NOT_ACTIVE`).
- **Sessions.** A new run starts a session whose id the app chooses (a UUID passed as `--session-id`, so it is known even if the CLI dies early); the CLI's announced session (`SessionStarted`) is recorded on the task. Follow-ups always resume the task's session (`TASK_NOT_RESUMABLE` without one, or when the provider cannot resume); retries resume it only once an earlier run of the task completed (a failed first run is retried in a fresh session).
- **Persistence.** Tasks and their logs live in the project's `project.db` (tables of schema v1, refined by schema v3: `format_version` on both, `run` on events) through the `TaskStore` port (`ProjectStore::tasks()`): one JSON row per task replaced as it changes, an append-only event log numbered by the store. When a project opens, tasks a stopped core left queued or running fail with `interrupted` (retry runs them again); tasks copied by « Duplicate » are re-attributed to the copy. Events are published as they are stored (`taskEventAppended`), every task change as `taskUpdated`.
- **Working folders.** Each run gets an empty folder `<app data>/agent-workdirs/<task id>/` (`AgentWorkspaces` port, `se_agents::FsAgentWorkspaces`): emptied when a run starts, removed when it ends, the same path for every run of a task (Claude Code keys sessions by working folder, so follow-ups find theirs). Leftovers of a crashed core are removed at startup.
- **Claude Code invocation.** `claude -p --output-format stream-json --verbose --tools "" --permission-prompts none --setting-sources "" --restricted --disable-slash-commands --strict-mcp-config --append-system-prompt-file <file> [--mcp-config <json> --allowedTools "mcp__simpleeffect__*"] [--model m] [--effort e] (--session-id <uuid> | --resume <uuid>)`, run in the task's folder. The **prompt goes to stdin** and the **instructions to a file** in that folder (`.simpleeffect-instructions.md`): on Windows `claude` is often a `.cmd` shim, and Rust refuses to pass arguments holding line breaks to batch files. The MCP config holding the task token is redacted from logs.
- **Isolation compatible with the subscription login.** Validated on Claude Code 2.1.317 (details in `crates/se-agents/src/providers/claude_code/CLAUDE.md`): `--setting-sources ""` and `--restricted` stop the user's settings files (hooks, permissions, default model) and auto-memory, `--disable-slash-commands` removes skills and commands from the agent's context, `--strict-mcp-config` keeps only our MCP server; authentication is not a setting and keeps working. `--safe-mode` is excluded (it also drops the servers given with `--mcp-config`), and so is `--bare` (API key only).
- **Environment.** When SimpleEffect was started from inside a Claude Code session (`CLAUDECODE` set: the development setup), the variables that session set for its children (`CLAUDE_CODE_*`, `CLAUDE_AGENT_SDK_*`, `ANTHROPIC_BASE_URL`…) are removed from the CLI's environment, user configuration excepted (`CLAUDE_CODE_OAUTH_TOKEN`, cloud provider switches, `ANTHROPIC_API_KEY`): otherwise our CLI would run as a nested child of that session.
- **Finding the CLI.** The path set in « Réglages → IA », else the PATH (`which`, PATHEXT-aware), else the usual install folders of the OS (`~/.local/bin`, Homebrew, npm prefixes, `%APPDATA%\npm`…): apps started from the desktop do not inherit the shell's PATH.
- **AI status.** `AiStatus { provider: ProviderInfo, installation, auth, capabilities }`: installation from `claude --version`, login from `claude auth status --json` (`loggedIn`, and only the account kind — never the e-mail or organisation). Checked in the background at startup, on demand (`refreshAiStatus`), after the executable setting changes, and corrected when a run fails for a missing login or CLI; published as `aiStatusChanged` when it changes. Submissions, retries and follow-ups are refused while the CLI is known missing or logged out (`AI_UNAVAILABLE`, saying how to fix it); an unknown login state is let through (the run will tell).
- **Failures.** Runs end with exactly one terminal event; the Claude Code adapter classifies errors from the `result` line or, without one, from stderr: `rateLimited`, `notAuthenticated`, `crashed`, `protocolError` (unreadable output), plus `cancelled`, `notInstalled` and the scheduler's `interrupted`. A run whose stream ends without a terminal event fails as `crashed`.
- **Cancellation.** The scheduler flips the run's cancel flag; the run calls the provider's `CancelHandle`; the adapter kills the whole process tree (job object on Windows, process group on Unix, both also on drop) and reports `cancelled`. A run that does not stop within 5 s is dropped (which kills it too).
- **Provider-agnostic UI.** The core describes the provider (`ProviderInfo { name, command, loginCommand, helpUrl }`); French texts interpolate it (« Ouvre un terminal, lance `{{command}}`, puis tape `{{login}}` »), so the renderer never names a CLI. The installation guide opens in the user's browser through the bridge's `openExternal`, which accepts `https:` URLs only.
- **Tests.** `ReplayProvider` (se-app `test-support`) replays scripted runs with simulated delays, holds and failures, and records specs and kills; every scheduler test uses it. The Claude Code adapter is tested on recorded stream-json fixtures and against a fake `claude` script (prompt on stdin, arguments, process-tree kill).

## Consequences
- Several tasks run in parallel with the user's edits; a core crash never leaves a task "running" forever, and nothing reruns without the user asking.
- The agent sees only what SimpleEffect gives it: no built-in tool, no user hooks or skills, no MCP server but ours, an empty folder. Its only way to act will be the MCP tools of prompts 18–19 (`AgentRunSpec.mcp` is optional until then).
- Adding a CLI means one adapter (`providers/<name>/`) plus a registration in se-core; the scheduler, persistence, settings and UI are reused.
- The adapter depends on Claude Code's flags, its stream-json format and its error wording: unknown lines are ignored (forward compatible), and the validated version and flags are recorded next to the adapter. Prompt 18 must check that `--restricted` keeps MCP tool calls working once the server exists.
- Session files of resumed agents accumulate in the CLI's own data folder (`~/.claude/projects/…`): the CLI's business, not cleaned by the app.

## Alternatives considered
- **One queue per project**: a project with many tasks could not be throttled against others, and the limit (protecting the user's usage quota) is global. Rejected.
- **Re-queueing interrupted tasks automatically at the next opening**: reruns spend quota and may edit the project unexpectedly long after the request. Rejected: they fail as interrupted and can be retried.
- **Prompt and instructions as arguments** (`-p <prompt>`, `--append-system-prompt <text>`): breaks with `.cmd` shims on Windows as soon as the text holds a line break. Rejected.
- **A temporary `CLAUDE_CONFIG_DIR` per run** for isolation: the CLI's login is tied to its configuration folder, so runs would be logged out. Rejected; setting sources and `--restricted` isolate without touching the login.
- **Reading the CLI's credentials file to know the login state**: contradicts « the app never reads credentials ». Rejected: the CLI is asked.
- **Polling the CLI's status**: needless process spawns; the status is checked at startup, on demand and when runs fail. Rejected.
