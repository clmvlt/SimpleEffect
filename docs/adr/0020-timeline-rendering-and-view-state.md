# 0020 — Timeline rendering, view state and shortcut contexts

- Status: Accepted
- Date: 2026-11-07

## Context
Prompt 10 builds the timeline's display and navigation: tracks, items with thumbnails and waveforms, a timecode ruler, the playhead, zoom and scroll, selection, in/out points, markers, sequence tabs, a central shortcut registry, and the first track and marker edits. It must stay at 60 fps with 500 items. Open questions: how to draw (DOM, canvas, PixiJS), how to keep zoom and scroll smooth over long sequences, where the view state (zoom, scroll, in/out points, playhead, track heights, active sequence) lives, how track and marker edits reach the core, and how a key like `I` knows whether it is meant for the timeline or another panel.

## Decision
- **DOM rows, virtualised, canvases only for pictures.** Each track is an absolutely positioned row; only the items crossing the visible range (plus 200 px of overscan) are rendered, found by binary search over the track's items (sorted by start and never overlapping, so their ends are sorted too). An item is a `ClipShell` (`@se/ui`) drawn only over its visible part (a 1-hour clip never makes a huge element), isolated with `contain: strict`. Video clips show tiles cut from the thumbnail sheet (CSS backgrounds), audio clips a waveform canvas computed from the cached peaks at the level giving at least one peak per pixel (the previous level stays drawn while the next one loads); clips narrower than 8 px draw no pictures. Canvases (waveforms, ruler, overview) read token values once (`shared/canvas/tokenValue`: `getComputedStyle` on every draw forced style recalculation and was the main cost) and are resized only when their size changes (waveform canvases in 128 px steps).
- **Virtual horizontal scroll and zoom.** The viewport is `{ pixelsPerSecond, scrollTime (flicks), width }`: Ctrl/⌘+wheel (and pinch) zooms around the pointer, Maj+wheel and horizontal swipes scroll, the slider is logarithmic, « Ajuster » fits the sequence, the overview strip (minimap) scrolls and zooms by its window. Wheel deltas are applied once per animation frame. Zoom goes from 0.01 px/s to 120 px per frame. Plain vertical wheel scrolls the tracks natively; Alt+wheel resizes the track under the pointer.
- **Display order.** Video tracks stack in document order (first = bottom), so they are listed top-down in reverse above a divider; audio tracks follow in document order (A1 first). « Add above/below » and drag reordering translate screen positions to document indices (`track-layout.ts`); reordering keeps the other kind's tracks in their places.
- **The playhead moves without re-rendering.** It has its own store (per sequence); the two playhead lines subscribe and set their own transform. It always sits on a frame start. Arrows step one frame (Maj: ten), ↑/↓ jump between edit points (sequence start and every item edge), Home/End go to the start and the content end. While dragged on the ruler it snaps (8 px) to edit points, markers and in/out points when snapping is on (`S`, toolbar magnet).
- **View state is a machine preference, never project data** (user's choice). Zoom, scroll, in/out points and playhead per sequence, track heights, the active sequence and the snapping toggle are saved in `localStorage` per project (`timeline.v1.project.<id>`, debounced) and restored when the project is shown again; they create no undo step. In/out points are half-open (`O` puts the out point after the frame under the playhead; a point crossing the other drops it) and are exposed with `useInOutSpan` as the scope of AI requests (prompt 20).
- **One protocol command per track or marker gesture** (`addTrack`, `removeTrack`, `updateTrack`, `reorderTracks`, `addMarker`, `updateMarker`, `removeMarker`), each one user transaction built by `ProjectService` with a label naming the change (`Mute track`, `Rename marker`…, translated by the renderer). The core names new tracks (`V3`, `A3`) and generates ids. Mute, solo, lock and visibility are document fields, so each toggle is an undo step.
- **Named shortcut actions with contexts.** `SHORTCUT_ACTIONS` lists every action with its contexts (`global`, `timeline`, `viewer`), default keys (macOS variants where they differ) and whether it repeats when held. Components bind handlers to actions; the registry runs an action when it is global or belongs to the active context — the region last clicked or focused (`ShortcutRegion`), the timeline claiming it when the editor opens. Symbols ignore Shift (layouts differ), ⌥ letters on macOS are read from the physical key. A test keeps the table free of conflicts; tooltips and the « Raccourcis clavier » help (`?`) are generated from it.

## Consequences
- With 500 items (`pnpm generate-test-project`), wheel zoom and scroll ran at the display's 144 Hz on the development machine (p95 frame 7 ms) and at p95 14 ms with all 500 items in view; JS per frame is about 5 ms.
- Decoding a waveform level runs on the main thread when the zoom crosses a level (a single 40 ms frame was seen): a worker can take it later (backlog).
- Clip interactions (drag, trim, cut) of prompt 11 plug into the same lanes: pointer handlers already stop at items, selection is shared through the feature's `index.ts`.
- View state does not travel with the project folder: another machine opens it fitted, without in/out points.
- Every new keyboard command is an entry in one table and appears in the help dialog for free; a conflicting default fails the tests.

## Alternatives considered
- **One big canvas (or PixiJS) for the whole timeline**: fastest to paint, but every hover, focus, menu, tooltip and accessible name would have to be rebuilt by hand, and component tests could not query items. Virtualised DOM met the frame budget.
- **Native scrollbars over a wide content element**: browsers cap element sizes around 33 million pixels (a long sequence at frame zoom exceeds it) and native scroll fights the anchored zoom.
- **View state in the document**: it would travel with the project and be visible to AI agents, but every zoom, resize or in/out change would become a transaction in the journal and the undo history. Rejected by the user.
- **A generic « apply operations » command from the renderer**: the renderer would generate ids and labels and could build arbitrary operations; specific commands keep ids and names in the core and validate intent. Prompt 11 may still add a generic edit command for clip gestures.
- **Shortcuts registered by raw keys in each component**: no listing, no conflict detection, and `I` would fire wherever the user was.
